## SVEXT — Scalable Vector Extension (Gen2)

SVEXT makes VLEN configurable. In Gen1 the vector length is fixed at 256 bits. In Gen2, hardware may support 128, 256, or 512-bit vectors.

### VLEN probing

Gen2 hardware reports its supported VLEN via `VSTATUS.SVL` (MSR 23, bits [31:8]). Software reads it at startup:

```asm
MSRRD r1, VSTATUS     ; bits [31:8] = SVL = supported VLEN
```

To stay portable, software should not assume a VLEN. The correct pattern is:

1. Read `SVL`
2. Compute `VLMAX = SVL / SEW`
3. Loop over `VLMAX` elements chunk-wise

### SEW table

| SEW | Elements (128-bit VLEN) | Elements (256-bit VLEN) | Elements (512-bit VLEN) |
|---|---|---|---|
| 8 | 16 | 32 | 64 |
| 16 | 8 | 16 | 32 |
| 32 | 4 | 8 | 16 |
| 64 | 2 | 4 | 8 |

### FP16 (half-precision)

Gen2 adds FP16 support — half the SEW of FP32, double the element count. `VSTATUS.VFP` (bit 2) is extended: value `0` = no FP, `1` = FP32/FP64, `2` = FP16 + FP32/FP64.

FP16 instructions: `V.FADD`/`V.FMUL` etc. accept `SEW = 16` (half-precision mode) and `V.CVT.HF`/`V.CVT.SF.HF` convert between FP32 and FP16 within the vector file.

### Gather / scatter

`V.LWG` (mop `010`) and `V.SWG` (mop `011`) are reserved in Gen1's VMEM class. Gen2 defines them as gather-load and scatter-store: each lane uses an independent address in a pointer vector, enabling strided and indirect access patterns.

## Backwards compatibility guarantee

Gen2 (SVEXT) is defined as an *extension* of V2. The guarantee:

1. **V1 binaries run unchanged on V2 and Gen2 cores.** The 32-bit encoding space is stable. V1 is the permanent subset.
2. **V2 binaries run unchanged on Gen2 cores.** Compressed, VSET, and power-managed code remains valid.
3. **VLEN-agnostic software runs everywhere.** Software that reads `SVL` and loops is portable across all VLENs.
4. **Gen1 cores never see Gen2 opcodes.** If software uses a Gen2 feature, it must probe first (`SVL`, `VFP`, gather-scatter presence in a future ID register).

## What stays VISION

The following are explicitly **not** part of BradISA plans, and have no timeline:

- Vector masking beyond the single `v0` register (Gen1/Gen2 keep one mask)
- Out-of-order vector execution
- Faster-than-one-per-cycle any ALU op (the walls are power, not encoding)
- Hyperthreading / SMT
- Silicon. BradISA is an ISA — it does not promise chips.
